ECC Project Flow

How a project moves from an idea to a merged pull request. You approve twice, once at the plan and once before the commit. Everything between runs on its own.

Already set up. Every session cut from main loads ECC at startup.

What happens, in order

Type commands in the session as /ecc:<name>. The orchestration commands in the next section run this whole sequence for you.

  • Runs on its own
  • You decide

  1. Intake

    Runs on its own

    Restates what you asked for. If you point it at a spec, it reads the document and pulls out the scope, the locked decisions and the feature list.

  2. Research

    Runs on its own

    Checks GitHub, vendor docs and package registries for something that already works, and prefers adopting it over writing it again.

  3. Plan

    Runs on its own

    Splits the work into thin vertical slices, so one path works end to end before the next one starts.

    planner /ecc:plan

  4. Gate 1: approve the plan

    You decide

    You read the task list and approve it or ask for changes. No implementation code is written before you do.

  5. Scaffold

    New projects only

    Stands up the first slice end to end, so every later slice has somewhere to land.

    /ecc:orch-build-mvp

  6. Implement

    Runs on its own

    Writes the failing test first, then the code, then tidies up. On a new project a generator builds each slice and an evaluator scores it against the spec until it passes.

    tdd-guide /ecc:tdd-workflow /ecc:gan-build

  7. Review

    Runs on its own

    Reviews every change. A security review joins when the change touches secrets, sign-in, file paths, external APIs, cryptography or database queries.

    code-reviewer security-reviewer

  8. Gate 2: confirm the commit

    You decide

    You see the diff summary and the proposed commit messages. Nothing is committed until you confirm.

  9. Commit

    Runs on its own

    One conventional commit per logical change, such as feat: or fix:. The loop returns to Implement for the next slice.

  10. Open the pull request

    Ask for it

    Ask the session to open a pull request into main. In a cloud session it does this with its GitHub tools, because ECC's /ecc:pr runs gh pr create, which cloud sessions block.

Pick your starting command

All five orch commands share the same sequence above. They differ in what they do first.

SituationCommandWhat it does first
You have a spec for a new project/ecc:orch-build-mvp <spec file>Reads the spec and orders it into vertical slices.
You only have an idea/ecc:plan-prd "<idea>"Writes a short problem-first spec to .claude/prds/<name>.prd.md.
A capability does not exist yet/ecc:orch-add-featureResearches and plans a new slice.
Something is broken/ecc:orch-fix-defectReproduces it as a failing test, then fixes it.
It works but should behave differently/ecc:orch-change-featureUpdates the tests to the new behavior first.
Same behavior, cleaner code/ecc:orch-refine-codeRestructures while the tests stay green.

A first project, start to finish

The quoted idea is an example. Replace it with your own.

  1. Start a session on a branch cut from main.

    ECC installs itself at startup. There is nothing to set up.

  2. Turn the idea into a spec.

    /ecc:plan-prd "personal finance dashboard: import bank statements, categorize spending, show a monthly view"

  3. Read the spec, then start the build.

    /ecc:orch-build-mvp .claude/prds/<name>.prd.md

  4. Gate 1. Read the slice plan.

    Approve it, or tell the session what to change.

  5. Gate 2. Read the diff summary and commit messages.

    Confirm to commit. Steps 4 and 5 repeat for each slice.

  6. Ask for a pull request into main.

    Merge it when you are happy. The next session starts from the merged work.

Good to know

The first shell command asks two questions

ECC's GateGuard hook asks the session to state your request and what its first shell command does. That is expected and happens once per session. To switch it off, set ECC_GATEGUARD=off.

Cloud containers start fresh

Keep specs and plans in the repo, such as .claude/prds/ or docs/. /ecc:save-session writes to ~/.claude, which a new container does not have.

Money data stays local

Put statements and exports in private/ or statements/. Both are git-ignored, so they cannot be committed by accident.
